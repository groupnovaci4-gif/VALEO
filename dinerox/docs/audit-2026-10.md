## Détail des problèmes

### É1 — Élevé (fonctionnement) : la connexion Google n'existe pas dans les APK
- **Ce qui ne va pas** : le bouton « Continuer avec Google » ne s'affiche que si `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` est fourni (`src/config/env.ts:43`). Aucun profil d'`eas.json` ne le fournit, les fichiers `.env` locaux sont vides pour Google, et le projet Firebase ne déclare **aucune application Android** (seulement une application Web).
- **Conséquence** : sur l'APK des testeurs, le bouton Google est absent. Le point 0.2 de la liste du test échouerait. Pas de faille de sécurité.
- **Preuve** : aucun identifiant `….apps.googleusercontent.com` dans le bundle de l'APK des testeurs ; `firebase apps:list` = 1 application WEB ; `grep -c GOOGLE eas.json` = 0.
- **Correction proposée** : créer dans Google Cloud un client OAuth Android pour `com.dinerox.app.staging` avec le SHA-1 ci-dessus (et plus tard pour `com.dinerox.app` avec la clé Play), et fournir les identifiants (publics) au build, par exemple dans `eas.json` › `staging.env`. **Nouvel APK**, aucun déploiement serveur. Action du fondateur dans la console Google Cloud.

### M1 — Moyen : les limites des formules ne sont appliquées que par l'application
- **Ce qui ne va pas** : comptes, objectifs, enveloppes, réserves, tontines du carnet, simulations, moments forts : la limite de la formule gratuite est vérifiée seulement dans `src/store/actions.ts` (`limit(…)`). Les règles Firestore n'en vérifient aucune.
- **Ce qu'un utilisateur pourrait faire** : avec une application modifiée ou un script, utiliser la formule gratuite au-delà de ses limites (fonctions payantes sans payer). Aucune donnée d'autrui n'est exposée.
- **Preuve (émulateur)** : un compte gratuit crée **6 comptes sur 6** (limite 3) et **5 objectifs sur 5** (limite 2) directement par Firestore.
- **Ce qui est déjà protégé côté serveur** : membres de famille (`inviteMember`), IA et voix (quotas), création de tontine partagée (Plus), « Plus offert ».
- **Correction proposée** : les règles Firestore ne savent pas compter des documents. Options : (a) déclencheurs Cloud Functions qui **signalent** au back-office un dépassement (sans rien supprimer) ; (b) App Check (M4) pour bloquer les applications modifiées ; (c) accepter le risque tant que le paiement n'existe pas. **Décision du fondateur.** Serveur (fonctions) pour (a).

### M2 — Moyen : l'anti-fraude du parrainage est contournable
- **Ce qui ne va pas** : « un appareil = un filleul » repose sur un `deviceId` **envoyé par le téléphone** (`referralApi.ts` : `deviceHash(data.deviceId, …)`), sans preuve d'appareil ; l'e-mail du filleul n'a pas à être vérifié ; la « semaine régulière » compte les jours avec la date `createdAt` **écrite par le téléphone** (`referral.ts:258-268`) et le fuseau horaire du profil (modifiable).
- **Ce qu'un fraudeur pourrait faire** : créer de faux filleuls par script (identifiants d'appareil inventés), simuler leur activité, et gagner des mois de Plus pour un parrain. Plafond actuel : 2 mois par mois (20 pour un ambassadeur).
- **Preuve (émulateur)** : 2 faux filleuls, `deviceId` inventés, e-mail non vérifié → tous deux **acceptés**, 2 inscriptions comptées chez le parrain.
- **Correction proposée** : (1) compter les jours d'activité avec l'heure du **serveur** (`syncedAt`) au lieu de `createdAt` ; (2) exiger un e-mail vérifié pour qu'un filleul soit **validé** (changement de comportement, à votre accord) ; (3) App Check (M4). Serveur (fonctions du parrainage) ; (2) et (3) touchent aussi l'APK.

### M3 — Moyen : les statistiques anonymes acceptent n'importe quoi
- **Ce qui ne va pas** : `analyticsEvents` accepte tout compte connecté, n'importe quel nom d'événement et des propriétés de **taille et de contenu libres** (`firestore.rules`, bloc `analyticsEvents`). La liste blanche des propriétés n'existe que dans l'application.
- **Ce qu'un attaquant pourrait faire** : gonfler les compteurs de l'écran admin (par ex. « partages » du parrainage), remplir la base (coût), y écrire des données personnelles.
- **Preuve (émulateur)** : un événement `referral_shared` avec un nom, un e-mail et une propriété de 50 000 caractères est **accepté**.
- **Correction proposée** : dans les règles, n'accepter que les noms d'événements connus, les clés de propriétés de la liste blanche (`ALLOWED_PROPS`) et des valeurs courtes (≤ 40 caractères). Test de règles. **Serveur (règles)**.

### M4 — Moyen : App Check n'est pas utilisé
- **Ce qui ne va pas** : l'API Firebase App Check n'a jamais été activée sur le projet ; aucune fonction n'exige App Check (`enforceAppCheck` absent du code).
- **Conséquence** : tout script muni d'un compte peut appeler les fonctions et écrire dans Firestore comme l'application (c'est ce qui rend M1, M2, M3 et F5 exploitables à grande échelle).
- **Preuve** : lecture de la configuration : « Firebase App Check API has not been used in project dinerox-app » ; aucun `enforceAppCheck` dans `firebase/functions/src`.
- **Correction proposée** : activer App Check avec Play Integrity (Android), l'intégrer à l'application, observer en mode « non imposé », puis l'imposer. Console + **nouvel APK** + **serveur**. Demande la publication sur Play pour Play Integrity complet.

### F1 — Faible : un partenaire peut signer une opération au nom d'un autre
- **Ce qui ne va pas** : à la création, les règles exigent `createdBy` « chaîne » mais pas `createdBy == moi` pour un administrateur ou un partenaire (`validBase`). Un enfant, lui, est bien limité.
- **Preuve (émulateur)** : le partenaire crée une dépense avec `createdBy` = l'administrateur → **accepté** ; l'enfant → refusé.
- **Correction proposée** : exiger `createdBy == request.auth.uid` à la création pour tous les rôles, après avoir vérifié qu'aucune écriture légitime de l'application ne pose un autre auteur. **Serveur (règles)**.

### F2 — Faible : trophées fabricables
- Les récompenses sont calculées par l'application et écrites par elle (`users/{uid}/rewards`). **Preuve** : trophée « objectif atteint » créé sans objectif → accepté. Effet : cosmétique (un trophée, partageable en image). **Correction** : accepter le risque, ou les faire écrire par une fonction. Serveur.

### F3 — Faible : mot de passe de 6 caractères
- L'application exige 8 caractères (`src/core/validation.ts:48`), Firebase n'en exige que 6 (aucune politique de mot de passe dans la configuration Auth). **Preuve (émulateur)** : inscription directe par l'API avec 6 caractères → acceptée. **Correction** : activer la politique de mot de passe Firebase (8 caractères minimum). Configuration Auth.

### F4 — Faible : un reste après la suppression de compte
- `deleteUserData` (`accountDeletion.ts`) n'efface pas `accountStatus/{uid}`, alors que la suppression par le back-office le fait (`backoffice/users.ts:294`). Le document contient : statut, date, identifiant du collaborateur, code de motif (pas de nom ni d'e-mail). **Preuve (émulateur)** : après `deleteAccount`, `accountStatus` est toujours là. **Correction** : l'effacer dans `deleteUserData`. Serveur (`deleteAccount`, `boDeleteUser`).

### F5 — Faible : aucun plafond d'essais pour les codes
- `tontineGroup` (`preview`, `requestJoin`) et `applyReferral` n'ont pas de compteur d'essais par compte. Deviner un code est irréaliste (31⁶ ≈ 887 millions de combinaisons), mais chaque essai coûte un appel. **Preuve** : code (`tontineGroupApi.ts:133-148`, `referralApi.ts:148-150`). **Correction** : un plafond quotidien d'essais par compte (comme `parseVoiceEntry`). Serveur.

### F6 — Faible : `localhost` autorisé pour l'authentification
- Domaines autorisés : `localhost`, `dinerox-app.firebaseapp.com`, `dinerox-app.web.app`, `dinerox-admin.web.app`. **Correction** : retirer `localhost` en production. Configuration Auth.

### F7 — Faible : permissions Android inutiles
- L'APK des testeurs déclare `SYSTEM_ALERT_WINDOW` (affichage par-dessus les autres applis) et `CAMERA`, inutilisées (les justificatifs viennent de la galerie). **Preuve** : `aapt2 dump permissions`. **Correction** : `android.blockedPermissions` dans `app.config.ts`. **Nouvel APK**.

### F8 — Faible : pages des liens sans en-têtes de sécurité
- Le site Hosting `links` (`firebase.json`) n'a aucun en-tête de sécurité (CSP, `X-Frame-Options`, `nosniff`), contrairement au back-office. Pas encore en ligne. **Correction** : ajouter les en-têtes avant de brancher `dinerox.app`. Hosting.

### F9 — Faible : code PIN
- Le PIN est bien protégé (empreinte salée, 2 000 tours de SHA-256, coffre sécurisé, 5 essais). Mais le délai de blocage dépend de l'horloge du téléphone (`security.ts`), et le PIN ne chiffre pas les données locales (lisibles sur un téléphone « rooté »). **Correction** : documenter, ou mesurer le blocage autrement. APK.

### F10 — Faible : dépendances
- `npm audit` (production) : application 36 alertes, fonctions 2, back-office 4. Presque toutes concernent des **outils de construction** (metro, expo-cli, node-forge, braces…) non livrés dans l'APK, ou `@grpc/grpc-js` (utilisé côté Node, pas par l'application ni le navigateur). Seule alerte touchant l'APK : `decode-uri-component`/`query-string` (via `expo-router`) — un lien piégé pourrait bloquer l'application (déni de service local). `uuid` (fonctions) : fonction vulnérable non utilisée. **Correction** : mise à jour avec le prochain SDK Expo. APK.

## Points d'information (pas des failles)

- **I1 — Voix** : par défaut, la reconnaissance vocale passe par le service du téléphone (Google, gratuit pour DineroX) qui peut traiter l'audio en ligne ; « sur l'appareil seulement » existe mais est désactivé par défaut. Aucun audio n'est envoyé à DineroX ni à un service payant (`speak`/ElevenLabs n'est pas déployé).
- **I2 — Journal d'audit du back-office** recopié dans Cloud Logging avec l'e-mail du collaborateur et le nom de la personne visée (`backoffice/context.ts:109`) : voulu pour l'audit ; durée de conservation de Cloud Logging à décider.
- **I3 — Suppression de compte** : les opérations saisies dans une famille qui continue restent à la famille, et les invitations envoyées par la personne gardent son prénom (`invitedByName`). À valider.
- **I4 — Profil** : un client peut écrire des champs inconnus dans son profil (jusqu'à 30 champs). Sans effet : aucun droit ne vient du profil (le rôle admin vient du jeton, `src/store/app.tsx:179`).
- **Base `eu-staging`** : sans protection contre la suppression ; inutilisée par l'application.

## Ce qui a été vérifié et qui est sain

- **Isolation des données** : un utilisateur ne lit ni n'écrit les espaces d'un autre ; familles : rôles admin / partenaire / enfant respectés (53 tests de règles + preuves de l'audit).
- **Champs réservés au serveur** : abonnement, droits offerts, parrainage, marqueur d'origine, membres d'un espace, compteurs d'usage (`usage/`), back-office (`bo*`) : jamais écrits par un client.
- **Tontine partagée** : lecture réservée aux membres, aucune écriture client, demandes visibles du seul demandeur et de l'organisateur.
- **Paiements** : aucune formule payante ne peut être attribuée par l'application (`verifyPurchase` volontairement non implémenté ; formule changée par le back-office avec permission et journal) ; « Plus offert » écrit par le serveur seul.
- **Fonctions** : toutes exigent une identité ; les fonctions admin exigent le droit admin ; le back-office exige une session à double vérification (`requireStaff`) sur chaque action, journalisée (chaîne d'audit) ; 20 instances maximum (plafond de coût).
- **IA** : clés uniquement côté serveur (secrets) ; consentement versionné ; quotas quotidiens ; transcription jamais journalisée.
- **Téléphone** : aucune clé secrète dans l'APK (seule la configuration publique Firebase) ; sauvegarde Android limitée aux préférences (le cache financier n'est pas sauvegardé) ; pas de trafic non chiffré déclaré ; liens entrants : seulement du préremplissage, rien n'est enregistré sans confirmation.
- **Authentification** : protection contre la révélation des adresses e-mail activée.
- **Back-office web** : en-têtes stricts en ligne (CSP, `X-Frame-Options: DENY`, HSTS, `nosniff`, `no-referrer`) ; aucun HTML venant d'un utilisateur (seules des icônes fixes).
- **Pages des liens** : tout est échappé, paramètres limités à `a-z 0-9 - _`, redirections vers des adresses fixes seulement (aucune redirection ouverte).
- **IAM** : un seul propriétaire humain, aucun accès public au projet.
- **Journaux des fonctions** : aucun identifiant ni donnée financière (sauf I2, voulu).
- **Tests** : `npm run check` 865, règles 53, fonctions 30, back-office 185, back-office web 6, export Android OK, **30 parcours e2e : 807 ✓ / 1 ✗** (`lot-b.js`, point h, existait avant).
